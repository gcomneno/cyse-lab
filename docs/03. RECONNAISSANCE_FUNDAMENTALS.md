# 03. Reconnaissance Fundamentals: Passive vs Active Evidence Collection

Status: Candidate learning module
Track: Foundations
Scope: CYSE Lab

## Purpose

This module formalizes reconnaissance as an evidence-collection discipline rather than a sequence of tools or menu options.

The central distinction is between **passive reconnaissance**, which gathers information without directly probing the target system, and **active reconnaissance**, which sends traffic or requests to the target or its infrastructure and therefore changes the operational and authorization boundary.

CYSE Lab remains white-hat and authorization-first: active reconnaissance is performed only against systems explicitly authorized for testing.

## Learning objective

A learner should be able to:

- distinguish passive from active reconnaissance;
- explain why the distinction matters operationally and ethically;
- identify the evidence produced by each step;
- record provenance and limitations of observations;
- avoid treating a tool output as a conclusion by itself;
- decide when a reconnaissance step requires explicit authorization;
- produce a short, reproducible write-up that separates observation from interpretation.

## Conceptual pipeline

```text
Target / scope
    |
    v
Authorization boundary
    |
    +--> Passive reconnaissance
    |      - public registration / WHOIS-style data
    |      - DNS records from public resolvers
    |      - public web metadata
    |      - public search / indexed information
    |
    v
Evidence + provenance
    |
    v
Decision gate
    |
    +--> Active reconnaissance, only if authorized
           - direct HTTP requests
           - service / port discovery
           - traceroute or path observations
           - direct fingerprinting / enumeration
    |
    v
Evidence + provenance
    |
    v
Interpretation / report
```

## Semantic boundary

The module must not teach:

> reconnaissance = run a collection of tools

It should teach:

> reconnaissance = collect scoped evidence, understand how it was obtained, preserve provenance, and distinguish observations from conclusions.

A command or tool may automate collection, but it does not become epistemic authority.

## Passive reconnaissance

Passive reconnaissance should be introduced as collection that does not intentionally interrogate the target host or application directly.

Examples may include:

- public registration information;
- public DNS data obtained through third-party or recursive infrastructure;
- certificate transparency data;
- indexed public pages and metadata;
- public threat-intelligence or reputation sources.

The exact classification of a source depends on how it is queried. The module should avoid claiming that a technique is universally passive merely because a tool labels it that way.

## Active reconnaissance

Active reconnaissance directly interacts with the target or its infrastructure.

Examples may include:

- direct HTTP requests and header inspection;
- service discovery;
- port scanning;
- active fingerprinting;
- direct subdomain or endpoint probing;
- traceroute/path probing.

Active reconnaissance requires the learner to verify the allowed target, scope, technique, and timing before execution.

## Evidence model

For every reconnaissance step, record at least:

- target and scope;
- technique;
- tool or source;
- timestamp when relevant;
- raw or minimally transformed observation;
- provenance;
- whether the collection was passive or active;
- authorization state for active steps;
- interpretation;
- uncertainty / limitations.

Recommended separation:

```text
OBSERVATION
What was actually returned or measured.

INTERPRETATION
What the observation may imply.

LIMITATION
What the evidence does not establish.
```

## Tooling policy

Tools such as `whois`, `dig`, `curl`, `traceroute`, `nmap`, `whatweb`, or wrappers that combine them may be used as learning instruments.

CYSE Lab should prefer **fewer tools with explicit semantics** over broad wrappers that hide what each operation does.

A wrapper such as WebInfo may be studied as an external learning/reference source, but its menu structure must not become the learning model for the module.

## Candidate exercises

### Exercise A — Evidence classification

Given a set of reconnaissance actions, classify each as passive, active, or context-dependent and explain why.

### Exercise B — Passive baseline

Collect only public/passive evidence for an authorized lab target and write a short provenance-aware report.

### Exercise C — Active delta

After explicit authorization, perform a minimal active reconnaissance step and compare what new evidence becomes available.

### Exercise D — Tool-output skepticism

Take one tool result and document at least one plausible interpretation and one limitation. The goal is to show that tool output is evidence, not conclusion.

## Verification criteria

The module is successful when the learner can:

- justify whether a collection step is passive or active;
- refuse or defer an active step when authorization is absent or ambiguous;
- reproduce the collection procedure;
- preserve enough provenance to understand where the evidence came from;
- distinguish observation, interpretation, and limitation;
- explain why multiple tools reporting the same claim do not necessarily constitute independent evidence.

## External reference provenance

Candidate inspiration observed from the WebInfo project/UI, which combines WHOIS, DNS, host lookup, traceroute, reverse DNS, SSL information, GeoIP, Nmap, HTTP headers/status, links, and subdomain-oriented operations.

Adoption rule:

- conceptual study: allowed;
- automatic integration: no;
- copy/paste of implementation: no without explicit source/license review;
- CYSE Lab owns its own learning objectives, semantics, exercises, and verification rules.
